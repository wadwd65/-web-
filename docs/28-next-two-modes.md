# 下一轮：简易模式与完整模式

记录日期：2026-10-31。状态：用户确定下一轮方向，本轮仅整理和持久化，尚未开发、测速或验收。当前应用版本仍为 v0.28。

## 用户反馈与优先级

用户报告两个问题：配置较差的电脑使用卡顿；现有入口与操作比较复杂，不方便新用户使用。用户提出下一轮增加简易模式与完整模式，让用户先直接提交问题，再由系统筛选合适的功能。

这次反馈调整旧的“下一轮先补动态背景”安排：下一轮优先解决轻量入口、问题分流与低配置性能；27号动态背景需求保留，随后在完整模式的性能预算内处理。不能继续给所有用户默认加载更多动态背景。

## 建议体验（细节为实施方案，不冒称已经用户验收）

用户后续明确更正：**默认完整模式，检测持续低帧/卡顿后自动切到简易模式，同时随时允许手动切回。** 这覆盖此前助手建议的“首访默认简易”。页首始终提供清楚的“简易模式 / 完整模式”切换，完整模式也要有可识别的快速问题入口。用户不必先弄懂八个模块；手动进入简易后可直接开始办事。模式偏好不保存问题原文或真实材料。

简易模式的主线：

1. 一个醒目的问题输入框，示例问题可点选，主操作“提交问题”。
2. 根据描述推荐对应事项，并用一句话解释“为什么推荐这个功能”。这里的“筛选”指八事务之间的问题分流，不是新增招聘或内容搜索平台。
3. 信息不足时只补问当前必要的问题，不让用户提前填写八套表单；不擅自补造金额、地区、身份或合同条件。
4. 明确展示下一步，进入同一套现有工具处理，结果与询问清单仍可复制或导出。

分类结果允许用户纠正；涉及多个事项时列出少量可执行步骤并让用户选择先办哪件；无法判断或超出范围时说明原因，提供八事务的文字入口。不自动跳转到猜测的页面，也不自动替用户填写已确认金额。

完整模式保留现有银蓝终端、三维事务阵列、入场回放、模型悬停/抽取和完整音乐播放器。完整不等于无限增加装饰，文字、入口和工作区仍要明确。

## 两种模式共用一套业务

模式改变入口、导航与视觉负担，八工具的计算/核对规则、当前填写、结果、询问清单和单audio共用。切换模式不清空本次内容、不重新计算出不同金额、不重播音乐，不复制两套业务状态和表单组件。

建议先提取共享业务状态与工具工作区，再分别实现轻量入口和完整视觉外层。保留旧路由可直接进入某个工具；模式与当前事务分别表达，避免切换模式被误做成返回首页或丢失当前步骤。

简易模式日常操作不加载或预热 Three.js 场景、模型、环境图、粒子、三维播放器及完整入场。可保留轻量音乐播放/暂停与五曲选择，复用单audio；只有用户明确打开完整三维播放器或切换完整模式时才按需加载相关资源。音乐不自动启播。

## 问题分流的真实能力边界

当前只有合同/租房核对的 API 客户端预留，尚无问题分类服务端、在线业务LLM或真实AI调用。下一轮需要新增并实际验证问题分流能力，不能把输入框、本地关键词模板或模拟返回称为已接通AI。

有服务端后：前端清楚表达问题将发往本项目后端，上传范围与用途可理解；密钥留在服务端；用户可取消，处理超时/失败/不可判断。分类结果应为可验证结构，限定到八事务ID、必要补问与解释，不允许模型输出任意导航地址或未经核验的确定性金额。

未配置在线服务时：明确显示当前能力，保留手动选择工具的正常入口。不能让“提交”无响应，也不能假装已经发送或成功分析。现有材料不会因为切换模式而自动上传。

## 性能工作必须落实到加载与生命周期

用户的低配卡顿反馈尚未在对应电脑测量，本轮不宣称已找到全部原因或已解决。源码静态检查显示当前入口与完整视觉外层耦合：App直接引用ExperienceWorkspace；ExperienceWorkspace除lazy场景外，还在挂载后立即import TaskArrayScene预热。仅把canvas设为不可见、只减几个粒子或减少CSS动画，不等于简易模式已经隔离重资源。

下一轮先记录现状，再检查：初始化/着色器编译、DPR与渲染尺寸、阴影和反射、透明层、粒子量、持续绘制、DOM写入、纹理内存和模式退出后的资源。以实际证据区分CPU、GPU、下载与状态重建的影响，不把所有不流畅都归为同一个原因。

完整模式增加可理解的轻量/标准画质档；后台、遮挡和关闭的场景暂停渲染；快速切换模式不能残留RAF、多个renderer或重复audio。降低画质与“减少动态”分别管理，不能假定用户系统偏好等于设备性能。故障或WebGL不可用时仍可回到轻量工具入口。

## 用户补充：默认完整，低帧自动转简易

确定要求：默认完整；测量当前页面实际运行的帧表现；持续卡顿自动降为简易；用户可以手动切回完整。以下检测窗口、阈值与防反复策略为待实测的实现方案，不是已经实现或已测得的设备结果。

- 场景首次可用后留短暂预热期，再开始有效采样；从已有活动渲染回调采集帧间隔，按实际采样时长计算FPS，不运行额外压力测试，不每帧刷新React界面。
- 初始调参建议：排除预热后，以1秒为观察窗口；连续5个有效窗口低于30 FPS时自动切简易，严重低于15 FPS持续2个有效窗口可更早处理。数值需要用低配置样本校准，不作为行业标准或用户已批准的硬指标。
- 仅统计前台可见、场景确实应持续绘制的阶段；页面隐藏、主动暂停、按需绘制的静止场景、系统“减少动态”导致的主动低频不能当作机器卡顿。隐藏或暂停后清除旧窗口，恢复时重新预热。首次加载/着色器准备的一次性停顿与持续低帧分开看，不能掉一帧就切。
- 自动切换时给轻提示：“当前运行较慢，已切换简易模式”，附“切回完整”按钮；不刷新页面，不清空输入或结果，不重播/重建audio，不重发正在处理的请求，保持当前事务和合理的输入焦点。
- 用户手动切回完整后，建议本次访问尊重该选择，不再反复强制切回简易；仍可提示运行较慢，用户也可手动转简易。自动降级只影响本次运行，不将后续访问的默认值偷偷改成简易，不自动在两种模式间来回升降。
- 自动切简易时停止重场景绘制并正确释放/停用相关资源，后续简易操作不得预热它们；显式切回完整时再按需加载并有准备状态。若WebGL不可用，显示原因并保留简易可操作路径。
- 现有src/performance-audit.ts只在?perf=1开启HUD，正常使用时关闭；其FPS用样本数量/固定2秒计算，启动不足窗口和主动少绘制时不能直接作为自动降级依据。下一轮独立实现轻量有效窗口判定，再复用可用的帧采样点。

浏览器动画回调在后台可能暂停，Page Visibility可用于识别页面隐藏状态，因此采样要过滤这些阶段。[requestAnimationFrame说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)、[Page Visibility说明](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)。这是检测当前网页体验，不能据此声称已测出整机硬件等级。

## 下一轮交付顺序与验收

1. 保存v0.28基线，在独立QA页测量现状，保留八工具、填写与音乐行为证据。
2. 拆出共享工作区；默认完整，完成简易/完整入口和可逆切换、持续低帧自动降级与明确的手动恢复，保留原完整模式视觉，不全面重画所有界面。
3. 完成问题提交、分类、补问、纠正与进入工具的完整流程；有后端才能验收真实AI分类，否则清楚标出该缺口。
4. 验证直接进入简易时不请求Three场景/GLB/三维封面资源；自动从完整降级后重场景停止且简易后续不再预热，无隐藏WebGL绘制；输入、编辑、搜索与复制导出正常。验证短暂掉帧、预热、后台、主动低频不误降级，持续低帧能降级，手动恢复不来回抢模式。
5. 以新用户完成一个事务为单位比较找入口/必填项/点击步骤；多事项和无法判断也能继续，不能只展示一个新的聊天框。
6. 对首次进入、闲置、分类提交、工具间切换、进出完整模式与音乐记录帧间隔/长任务/资源加载等实际证据，在低配样本或明确说明限制的模拟条件下比较前后；不以主力电脑通过代替低配验证。
7. 保留本次填写、询问清单、音乐曲目/进度与单audio；反复切换无资源持续累积；控制台无新错误；桌面端自检。仍不开发手机端。
8. 两模式与性能可用后，再按27号给完整模式补低负担持续背景动态。最终审美与易用性需实际审核，文档不代表完成。
